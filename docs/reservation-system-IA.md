# 餐廳預約系統 — 資訊架構（IA）

> 依據 FigJam「餐廳預約系統」前期研究產出：競品分析（inline、OpenTable、EZTABLE、TableCheck、iCHEF）、Persona、User Story、Problem Statement、Goal Statement 及客製化功能需求。
>
> 版本：v1.0（2026-07-16）

---

## 一、設計原則

整套架構以「直覺、簡單、易上手」為最高原則，落實方式如下：

| 原則 | 落實方式 |
|------|----------|
| C 端零摩擦 | 免下載 App、免註冊，從 LINE / IG / Google 地圖一鍵進入，**3 步內完成訂位** |
| B 端單一入口 | 一台 iPad 統籌訂位、候位、桌況、結帳；首頁即「今日營運」，不需切換多套工具 |
| 內場零干擾 | KDS 只顯示「今天要備什麼、每桌有什麼特殊需求」，不出現管理功能 |
| 自動分流 | 依品牌模式開關自動決定訂位流程，使用者不需要自己選模式 |
| 資訊一致 | 前台輸入的資料（時間、人數、訂金）單一來源，同步映射至 Discord 推播、POS、KDS |

## 二、系統總覽

```
餐廳預約系統（三品牌共用平台）
│
├── C 端｜智慧預約入口（消費者）
├── B 端｜現場與集團管理中心（外場／櫃檯／店長／總部）
├── 內場｜生產端同步（主廚／備料，KDS）
│
└── 共用底層服務
    ├── 集團 CRM（統一顧客檔案、跨品牌點數）
    ├── 金流服務（預授權／訂金／預付餐費／退款）
    ├── 通知中樞（Discord / LINE 訊息推播）
    └── 數據中心（銷量追蹤、備料報表、CSV 自主下載）
```

**三品牌模式**（由後台「品牌模式開關」控制訂位流程）：

| 品牌 | 定位 | 鎖定訂位流程 | 目的 |
|------|------|--------------|------|
| 喀啡人 CAFELUX | 高翻桌率咖啡廳 | 先訂位 → 後點餐 | 維持高流量流暢度 |
| 第28區 | 高客單中餐宴席 | 先點餐 → 再訂位 | 以訂餐取代訂金，保護利潤 |
| 明珠格 | 精緻蔬食 | 同時點餐＋訂位 | 一站式結算 |

## 三、C 端｜智慧預約入口

**目標使用者**：張小姐（聚餐主辦人）、小優（跨品牌常客）
**核心體驗**：免 App、免註冊、一鍵訂位、預訂餐點取代沒收訂金

```
C 端
│
├── 1. 進入點（免註冊）
│   ├── LINE 官方帳號
│   ├── Google 地圖「訂位」按鈕
│   ├── IG 連結
│   └── 品牌官網
│
├── 2. 選擇餐廳（品牌頁）
│   ├── 品牌介紹／菜單瀏覽
│   └── 進入訂位（系統依品牌模式自動分流 ↓）
│
├── 3. 訂位流程（三選一，由後台鎖定，消費者無感切換）
│   │
│   ├── 模式 A｜先點餐再訂位（第28區・宴席）
│   │   ├── 選擇大菜／套餐（如佛跳牆）
│   │   ├── 選擇日期・時段・人數
│   │   └── 支付：信用卡預授權（凍結不扣款）／轉帳／預付餐費
│   │
│   ├── 模式 B｜先訂位後點餐（喀啡人）
│   │   ├── 選擇日期・時段・人數
│   │   ├── 訂位成功
│   │   └── 收到「預約點餐連結」→ 引導預先點購
│   │
│   └── 模式 C｜同時點餐訂位（明珠格）
│       └── 選位＋選餐 → 一站式結算
│
├── 4. 訂位共用元素（三種模式皆有）
│   ├── 人數選擇 → 系統自動媒合桌位（依桌位容納區間）
│   ├── 特製需求備註欄
│   │   ├── 文字輸入（如「慶生特製低糖蛋糕」）
│   │   └── 留下電話 → 供餐廳聯繫確認
│   └── 滿位彈性處理（Waitlist 2.0）
│       ├── 後台開啟人工候補 → 按鈕不變灰，顯示
│       │   「請稍後，我們即將轉人工幫您確認」
│       └── 後台關閉 → 直接顯示額滿（預設行為）
│
├── 5. 訂位確認與通知
│   ├── 確認訊息（Discord API 或 LINE）：時間・人數・已收訂金
│   │   → 與櫃檯 iPad 顯示內容完全一致
│   └── 自動提醒：訂位前提醒／變更・取消連結
│
└── 6. 會員中心（統一帳號，跨三品牌）
    ├── 我的訂位（查詢／修改／取消）
    ├── 跨品牌點數（喀啡人集點 → 抵扣第28區宴席）
    ├── 用餐喜好與備註（不吃牛、兒童椅…，訂位時自動帶入）
    └── 消費紀錄
```

## 四、B 端｜現場與集團管理中心

**目標使用者**：阿明（外場領班）、櫃檯接待、店長、總部管理層
**核心體驗**：一台 iPad 看完今日全局；設定類功能收在「設定」，日常操作不被干擾

```
B 端
│
├── 1. 今日營運（首頁・現場 iPad 主畫面）
│   ├── 今日訂位總覽（時間軸／清單）
│   ├── 即時桌況圖（客製化桌圖）
│   │   ├── 智慧控位引擎：依人數自動媒合最優席次
│   │   │   （10 人自動過濾 2-4 人桌 → 媒合包廂／大圓桌）
│   │   └── 手動調桌／VIP 控位
│   ├── 現場候位排隊
│   │   ├── 自動排號
│   │   └── 一鍵「叩客」簡訊通知回店
│   └── 結帳：自動扣抵預付訂金／餐費，只收尾款
│
├── 2. 訂單管理
│   ├── 訂位訂單列表（狀態：已預訂／已收訂金／已確認特製／已入座／已完成／未到）
│   ├── 待確認項目（特製需求）
│   │   ├── Discord 推播標註「待確認項目」
│   │   ├── 點「與顧客聯繫」→ 系統自動帶出顧客手機
│   │   └── 確認後手動更新為「已確認特製」
│   ├── 人工候補清單（滿位轉人工的訂位請求）
│   └── 取消與退款處理（No-show 依政策自動扣違約金）
│
├── 3. 商品庫（BOM & 銷量追蹤）
│   ├── 單樣商品 SKU（脆皮雞、咖啡…：名稱／價格／狀態）
│   ├── 組合套餐 Bundles
│   │   ├── 建立時必須掛載單樣商品（如「父親節 6,800 方案」含脆皮雞 ×1）
│   │   └── 售出一套 → 自動累計所掛單品的販售數量
│   └── 菜單管理（上下架、預點菜單設定）
│
├── 4. 桌位管理
│   ├── 客製化桌圖編輯
│   ├── 桌位容納區間（1 號桌 2-4 人、10 號包廂 8-12 人）
│   └── 自動媒合規則
│
├── 5. 顧客 CRM（集團層級）
│   ├── 統一顧客檔案（一人一檔，跨三品牌）
│   │   ├── 消費習慣・喜好標籤（不吃辣、坐室外…）
│   │   └── 跨品牌消費紀錄（點餐＋訂位資料串接）
│   ├── 點數管理（跨品牌互通、集點與抵扣）
│   ├── RFM 標籤與行銷（首次訂位／60 天未回訪／壽星 → 自動發送誘因）
│   └── 黑名單（惡意放鳥自動拒訂）
│
├── 6. 報表與數據
│   ├── 單品銷量排行（含套餐連動累計 → 主廚看得到單品熱度）
│   ├── 訂位／候補／No-show 統計
│   └── 數據自主下載（完整 CSV，客資名單帶得走）
│
└── 7. 設定（店長／總部）
    ├── 品牌模式開關（鎖定訂位流程 A / B / C）
    ├── 人工候補開關（依當天人力決定開／關）
    ├── Discord 推播設定
    │   ├── 餐廳訊息模板選擇
    │   └── 頻道綁定（訂位成功／已收訂金／時間人數 自動推播）
    ├── 金流與取消政策（預授權、訂金比例、違約金、退款期限）
    ├── 營業時段與可訂位時段
    └── 帳號權限（外場／櫃檯／店長／總部）
```

## 五、內場｜生產端同步（Kitchen / KDS）

**目標使用者**：陳師傅（行政主廚）、備料人員
**核心體驗**：只看兩件事——「明天備什麼」「這桌有什麼特殊需求」

```
內場（KDS）
│
├── 1. 即時備料報表
│   ├── 自動彙整預購單品數量（佛跳牆 ×N、脆皮雞 ×N…）
│   ├── 依日期檢視（今日／明日），供主廚精準採購、降低損耗
│   └── 前一天自動產出「明日預訂餐點報表」
│
├── 2. 訂單看板（出餐）
│   ├── 依訂位時間排序的預點餐點
│   ├── 訂位備註自動帶入（過敏、全素、去五辛、兒童餐具…）
│   │   （同步顯示於 KDS 螢幕或 POS 小白單）
│   └── 出餐狀態更新（備餐中／已出餐）
│
└── 3. 特製餐點提示
    └── 「已確認特製」項目連動顯示（如：慶生低糖蛋糕）
```

```
共用服務
│
├── 金流服務
│   ├── 信用卡預授權（凍結額度不扣款，No-show 自動扣違約金）

├── 通知中樞
│   ├── Discord 推播（B 端工作協作＋C 端確認副本）
│   │   └── 前台資料 → 映射餐廳模板 → 發送，保證資訊一致
│   ├── LINE 訊息（C 端確認與提醒）
│   └── 簡訊（候位叩客）
│
├── 集團 CRM 資料庫
│   └── 統一顧客檔案・點數帳本・標籤，供三品牌共同讀寫
│
└── 數據中心
    ├── 銷量連動（套餐 → 單品自動累計）
    ├── 備料彙整（→ KDS 報表）
    └── 100% 數據自主下載（CSV）
```

## 七、關鍵資料流（資訊一致性）

```
消費者訂位（C 端輸入：時間・人數・預點・備註・付款）
        │
        ▼
訂單資料庫（單一來源 Single Source of Truth）
        │
        ├──► Discord 頻道推播（依餐廳模板：訂位成功／已收訂金）
        ├──► C 端確認訊息（Discord / LINE，內容與櫃檯完全一致）
        ├──► B 端 iPad（今日營運・桌況・自動媒合桌位）
        ├──► POS（備註與預點自動帶入，結帳自動扣抵預付款）
        ├──► KDS（備料報表・出餐備註）
        └──► CRM（消費紀錄・點數累計・RFM 標籤）
```

## 八、待確認事項（建議下一步討論）

1. **POS 串接方式**：與現有 POS（如 iCHEF）API 串接，或自建輕量 POS 模組？
2. **LINE vs Discord 對 C 端的角色**：C 端確認訊息以 LINE 為主、Discord 為輔，還是兩者並行？
3. **會員中心是否為 MVP 範圍**：跨品牌點數涉及金流與帳本設計，是否列入第一期？
4. **多語系需求**：是否需支援英日語（參考 TableCheck 18 國語系）？
5. **權限層級細節**：總部 vs 單店店長在「設定」的權限邊界。
